# Среды передачи данных из нескольких носителей

Мы всё ближе подходим к задаче объединения всех абонентов в единый интернет. Однако для начала рассмотрим более простую задачу.

Пусть имеется несколько сред передачи данных с одним и тем же видом носителя. Физически это отдельные взаимодействующие множества абонентов. Задача будет следующая: обеспечить на интерфейсном уровне единую среду, работающую поверх носителя, в которой физически разные сети воспринимаются устройcтвами в виде единой локальной сети.

Логичное продолжение — объединение множества сред на _разных_ носителях. Но… на поверку это оказывается задачей совершенно другого уровня: если интерфейсные протоколы значимо отличаются, нет смысла изобретать преобразователь любого формата фреймов в любой, который вдобавок пытается сохранить уникальность идентификаторов. Гораздо логичнее поднять решение вопрос на уровень выше — туда, где решается задача уникальной идентификации всех абонентов неоднородной сети. Об этом бы поговорим в следующей главе.

# Коммутация фреймов

Перейдём к решению. Обычно настройка маршрутизации пакетов (а именно она требуется для объединения нескольких сред в единую сеть) ложится на сетевой уровень. При получении нового пакета промежуточный узел сети, _маршрутизатор_ , декапсулирует его до сетевого уровня, проверяет IP-адрес получателя, после чего инкапсулирует всё обратно и перенаправляет дальше по сети в сторону целевого абонента.

Цель данной главы — показать, каким образом задача объединения нескольких сред может быть решена непосредственно на интерфейсном уровне, и какие важные ограничения могут при этом возникнуть. Перенаправление пакета между абонентами сети называется _маршрутизацией_ как в общем случае, независимо от уровня протокола, так и конкретно на сетевом уровне, который мы пока не рассматриваем. Поэтому перенаправление пакетов интерфейснного уровня — фреймов — мы назовём _коммутацией_, а устройства, которые решают такую задачу — _коммутаторами_.

Для настройки коммутации пакетов необходимо использовать специальные устройства  — _хаб_ и _мост_. Это могут быть как специализированные устройства, предназначенные исключительно для коммутации, так и многофункциональные абоненты сети, вплоть до компьютеров общего назначения под управлением Linux. Более правильно будет сказать, что коммутатор — это _роль_, которую данный абонент сети играет.

## Хаб и сетевой мост

[Хаб](https://ru.wikipedia.org/wiki/%D0%A1%D0%B5%D1%82%D0%B5%D0%B2%D0%BE%D0%B9_%D0%BA%D0%BE%D0%BD%D1%86%D0%B5%D0%BD%D1%82%D1%80%D0%B0%D1%82%D0%BE%D1%80), он же _сетевой концентратор_ — это устройство, которое, получив пакет на один интерфейс, ретранслирует его во все остальные.

Для настройки хаба на Linux-машине необходимо всего лишь подключить постоянный _неразборчивый режим_ и пересылать все приходящие данные на все порты кроме, быть может, порта-источника. Такой режим работы хаба идентичен работе общей шины между устройствами. И, как и общая шина, хаб приносит достаточное количество трудностей передачи: именно для него верно правило «50% загруженности по времени — неработающая сеть».

Более универсальным решением является [сетевой мост](https://ru.wikipedia.org/wiki/%D0%A1%D0%B5%D1%82%D0%B5%D0%B2%D0%BE%D0%B9_%D0%BC%D0%BE%D1%81%D1%82). Он также поддерживает неразборчивый режим работы, однако не строит работу только на нем.

Сетевой мост поддерживает _таблицу абонентов_. Это динамически обновляемая таблица соответствия между MAC-адресами и сетевыми интерфейсами, за которыми находятся абоненты с этими MAC-адресами. В случае **не** Ethernet таблица может описывать соответствия других идентификаторов и интерфейсов, но схема работы останется идентичной.

Если мост получает широковещательный фрейм, или фрейм, предназначенный неизвестному получателю, он вынужден работать как хаб — ретранслировать фрейм во все интерфейсы. Однако каждая такая ретрансляция запоминает, за каким интерфейсом находился _отправитель_ и заполняет (или обновляет) строчку в таблице абонентов. Пока абонент не удалился из таблицы, ретрансляция пакета ему _как получателю_ будет идти только по одному интерфейсу. 

При включении моста, когда таблица абонентов ещё не заполнена данными, первые фреймы будут рассылаться широковещательно. Потенциально эту особенность работы можно использовать при сетевой атаке.

## Контроль работы коммутаторов

При работе множества коммутаторов в одной локальной сети могут возникать различные проблемы передачи.

Самая простая из них — зацикливание пакетов между мостами. Для её решения разработан специальный протокол [`STP`](https://ru.wikipedia.org/wiki/STP) - `Spanning Tree Protocol`. Технически он отсекает доступ к некоторым интерфейсам у мостов, оставляя только полносвязное дерево абонентов.

Для предотвращения сетевых атак на таблицы абонентов разработаны различные antispoof-алгоритмы, позволяющие вычислять и блокировать источники атаки, закрывая им доступ к сети. Например, такую защиту обеспечивает [`firewall L2`](https://wiki.nftables.org/wiki-nftables/index.php/Bridge_filtering) в высокоуровневой утилите [`nftables`](https://wiki.nftables.org/). На интерфейсном уровне устанавливается специальный фильтр фреймов, основанный на MAC-адресации. К сожалению, из-за возможности смены MAC-адресов у большинства устройств данный способ не обеспечивает полной защиты от атак.

## Создание моста

На виртуальных машинах настроим взаимодействие двух абонентов через мост. Для этого создадим три устройства со следующими соединениями:

```console
srv:
        eth1: net1
client:
        eth1: net2
bridge:
        eth1: net1
        eth2: net2
```

Запустим наши машины. После запуска «поднимем» сетевые интерфейсы на машинах srv и client. 

`srv`
```console

[root@srv ~]#
```

`client`
```console

[root@client ~]#
```

# VLAN - Virtual Local Area Network


При обсуждении VLAN стоит различать два определения этого термина. «Инженерный» термин VLAN означает группу интерфейсов, объединённых в единую среду передачи данных, которая изолирована от других групп интерфейсов. Реализовать такое поведение коммутаторов можно по-разному. Например, создание таких групп может быть просто выведено в интерфейс управления коммутатором. 

Другой вариант реализации — снабдить каждый фрейм дополнительным полем, в котором явно указывать такую изолированную группу, и принимать решение о коммутации на основании этого поля. Такую задачу решает семейство протоколов [IEEE_802.1Q](https://en.wikipedia.org/wiki/IEEE_802.1Q). Использование в сети таких модифицированных 802.1Q-фреймов — это другое определение термина VLAN,  «теоретическое».

![](Attached_materials/IEEE_802_1Q.png)

На текущий момент технологию IEEE_802.1Q поддерживают все сетевые карты. Более того, модификации протокола способны обработать фреймы с двумя тегами подряд и другими надстройками VLAN.

Большая часть текстов про VLAN — это методички по настройке разнообразных топологий на разнообразном «железе», так что в них используется «инженерное» понимание термина. Как следствие, возникают понятия «тегированного» VLAN-а (т. е. канала с поддержкой протокола 802.1Q и определённым VID в теге фрейма) и «нетегированного» VLAN-а (канала «простыми» фреймами без тега 802.1Q, объединение и разделение которых диктуется исключительно ПО на коммутаторе). Мы будем придерживаться «теоретической» терминологии: фраза «фрейм из VLAN-а такого-то» означает 802.1Q-фрейм с определённым VID, а просто «фрейм» — просто фрейм.

На практике использование IEEE_802.1Q-протокола удобно при создании независимых сетей из нескольких сред передач данных каждая, работающих на одном физическом оборудовании. Пример организации двух VLAN на одном физическом мосту продемонстрирован на картинке:

Для начала на каждом из абонентов необходимо настроить виртуальные интерфейсы, через которые будут проходить фреймы с соответствующим тегом. При отправке данных фреймы, проходящие через VLAN-интерфейс, будут получать заголовок и выходить в канал уже с тегом. При получении данных все фреймы с соответствующим VLAN-тегом будут направляться в эти интерфейсы, где с них будет сниматься тег.

`srv`
```console
[root@srv ~]# ip link add link eth1 name vlan5 type vlan id 5  
[root@srv ~]# ip link set vlan5 up  
[root@srv ~]#
```

`client`
```console
[root@client ~]# ip link add link eth1 name vlan5 type vlan id 5  
[root@client ~]# ip link set vlan5 up  
[root@client ~]#
```

На bridge также сделаем VLAN-интерфейсы, чтобы отдельно проводить трафик VLAN по устройству. Между этими интерфейсами внутри bridge фреймы передаются без тега — он снимается при выходе с одного интерфейса и вновь надевается при входе в другой. Общий трафик в устройстве не будет отличим от трафика с тегами. Для их разделения и делается отдельный мост, хотя формально новые интерфейсы можно было привязать и к старому.

`bridge`
```console
[root@bridge ~]# ip link add link eth1 name vlan51 type vlan id 5  
[root@bridge ~]# ip link add link eth2 name vlan52 type vlan id 5  
[root@bridge ~]#   
[root@bridge ~]# ip link add dev brvlan type bridge  
[root@bridge ~]# ip link set vlan51 master brvlan  
[root@bridge ~]# ip link set vlan52 master brvlan  
[root@bridge ~]#
[root@bridge ~]# ip link set vlan51 up  
[root@bridge ~]# ip link set vlan52 up  
[root@bridge ~]# ip link set brvlan up  
[root@bridge ~]#
```

## Работа с VLAN

Теперь реализуем более сложную сетевую структуру с использование VLAN:

![](Attached_materials/VLAN.png)

В сети будет настроено два VLAN-a. Между мостами, соединяющими абонентов из разных VLAN будет передача фреймов с тегами для отделения абонентов разных VLAN друг от друга. Получится, что физически устройства из разных VLAN достижимы, однако на программном уровне доступа друг к другу у них нет. Канал (и интерфейс, к нему присоединённый), по которому передаются фреймы разных VLAN-ов, на «инженерном» языке имеет отдельное название —  «транк» (trunk), т. к. под инженерное определение VLAN не подходит.

Создадим все устройства для топологии:
```console
hostA:
        eth1: netA
hostB:
        eth1: netB
hostD:
        eth1: netD
hostE:
        eth1: netE
bright:
        eth1: netA
        eth2: netB
        eth3: netC
bleft:
        eth1: netD
        eth2: netE
        eth3: netC
```

# Фильтрация тегов на уровне моста

Во всех наших примерах мы использовали интерфейс bridge исключительно для связывания интерфейсов. Сама фильтрация VLAN осуществляется при проходе пакета через соответствующий интерфейс.

Сам сетевой мост — это достаточно ёмкое по технологиям устройство. Одна только поддержка STP требует внутреннего отслеживания и обработки пакетов для поддержания корректного остовного дерева. Поэтому неудивительно, что сам bridge-интерфейс умеет отслеживать VLAN-метки. Пример такой настройки и управления 802.1Q-фреймами представлен в лабораторных работах на эту тему (на [Usamg1t.Github.io](https://usamg1t.github.io/Nets_ASVK_Labs/04_VLAN/%D0%9D%D0%B0%D1%81%D1%82%D1%80%D0%BE%D0%B9%D0%BA%D0%B0%20VLAN.html) или в [документации](https://docs.altlinux.org/ru-RU/labwork/0.1/html/nets-laboratories/VLAN.html) «Базальт СПО»).
